## Node.js — "Мозг сервера"

**Простыми словами:**
Раньше JavaScript работал ТОЛЬКО в браузере — ты открываешь сайт, браузер запускает JS-код на твоём компьютере.
Node.js — это возможность запустить JavaScript прямо на сервере, без браузера.

**Аналогия:**
Представь повара, который умеет готовить только дома (браузер). Node.js — это когда того же повара пустили работать в ресторан (сервер).

**Главная фишка — он не ждёт:**
Обычный сервер работает так: пришёл запрос от пользователя — сервер занялся им, все остальные ждут.
Node.js работает по-другому: пришёл запрос — начал обрабатывать — пока база данных думает, Node.js уже принимает следующий запрос.

**Аналогия:**
Официант в кафе. Он принял заказ у стола 1, пошёл на кухню, передал заказ, и пока повар готовит — он уже принял заказ у стола 2 и стола 3. Он не стоит и не ждёт у плиты.

**В нашем проекте:**
Когда пишешь `node server.js` — это запускает весь сервер. Node.js начинает слушать порт 3000 и ждёт запросов от браузера.

## Express.js — "Диспетчер запросов"

**Простыми словами:**
Express.js — это библиотека, которая говорит серверу: "Если пришёл запрос на /login — вызови эту функцию. Если пришёл запрос на /tournaments — вызови другую функцию."

**Аналогия:**
Express — это телефонная станция. Звонок пришёл? Она смотрит — кому? И соединяет с нужным отделом.

**Middleware — цепочка охранников:**
Каждый запрос от браузера проходит через несколько "охранников" по очереди:
1. Первый охранник: CORS — "этот браузер вообще имеет право обращаться к нам?"
2. Второй охранник: JSON — "разбери тело запроса, чтобы мы поняли что внутри"
3. Третий охранник: JWT — "у тебя есть токен? Ты вообще залогинен?"
4. Только потом: контроллер — "хорошо, вот твои данные"

**В нашем проекте:**
```
GET /api/tournaments → Express → проверка JWT → tournamentController.getTournaments()
POST /api/auth/login → Express → loginLimiter → authController.login()
```

## MySQL — "Большая таблица с правилами"

**Простыми словами:**
MySQL — это база данных. Представь Excel с множеством листов (таблиц), где каждая строка — это одна запись (один пользователь, один турнир, один матч).

**Аналогия:**
Школьный журнал:
- Один лист — "Ученики" (id, имя, класс)
- Другой лист — "Оценки" (id, id_ученика, предмет, оценка)
- Они СВЯЗАНЫ: в "Оценках" написано id ученика, и по этому числу мы находим его в листе "Ученики"

**Реляционная база данных — что это значит:**
"Реляционная" = данные связаны между собой через числа (id).
Вместо того чтобы в каждом матче писать "Armenia Cup 2026", мы пишем `tournament_id = 5`. И по числу 5 находим турнир в таблице tournaments. Это экономит место и не позволяет данным рассинхронизироваться.

**mysql2 — переводчик:**
Node.js не умеет сам разговаривать с MySQL. mysql2 — это переводчик между ними. Ты пишешь JavaScript-код, mysql2 переводит его в SQL-запрос, отправляет в базу, получает результат и отдаёт обратно в JavaScript.

**Connection Pool (пул соединений):**
Представь, что к базе данных надо каждый раз "дозваниваться" (устанавливать соединение). Это медленно. Pool — это 10 уже готовых линий связи, которые всегда открыты. Пришёл запрос — берём свободную линию, использовали — вернули обратно. Быстро.

## bcrypt — "Мясорубка для паролей"

**Простыми словами:**
Когда пользователь регистрируется и вводит пароль "football123", мы НЕ сохраняем "football123" в базу. Это опасно — если базу взломают, все пароли утекут.

bcrypt превращает "football123" в что-то вроде: `$2b$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LPSs` — и вот ЭТО сохраняется в базу.

**Главное свойство — НЕОБРАТИМО:**
Мясорубка перемалывает мясо — обратно уже не восстановишь. bcrypt работает так же. Из хеша нельзя получить исходный пароль.

**Как тогда проверить пароль при входе?**
При логине bcrypt берёт введённый пароль "football123" и хеш из базы, и сравнивает их по специальному алгоритму. Если "подходят" — пускает. Если нет — отказывает.

**Соль (salt):**
Чтобы два пользователя с одинаковым паролем "123456" имели разные хеши — bcrypt добавляет случайный мусор (соль) перед хешированием. Поэтому даже одинаковые пароли дают разные хеши.

**Rounds (10):**
Чем больше rounds, тем дольше вычисляется хеш. Мы используем 10. Это специально — чтобы хакер не мог быстро перебирать миллионы паролей. Каждая попытка занимает ~100 мс.

## JWT (JSON Web Token) — "Пластиковый пропуск"

**Простыми словами:**
После входа на сайт нам надо как-то доказывать серверу при каждом следующем запросе, что мы уже залогинены. JWT — это пропуск, который сервер выдаёт при входе.

**Аналогия:**
Ты пришёл в клуб, показал паспорт на входе. Охранник проверил и дал тебе браслет на руку. Теперь внутри клуба ты везде показываешь браслет — никто паспорт больше не просит. Браслет = JWT токен.

**Структура токена (три части через точку):**

`eyJhbGciOiJIUzI1NiJ9.eyJpZCI6MSwidXNlcm5hbWUiOiJBcm1hbiJ9.xK8mN2pQ`

1. **Заголовок** (Header) — алгоритм подписи: "я подписан алгоритмом HS256"
2. **Данные** (Payload) — информация: `{ id: 1, username: "Arman", role: "organizer" }`
3. **Подпись** (Signature) — цифровая подпись, что токен не подделан

**Как проверяется:**
Сервер знает секретный ключ (в .env: `JWT_SECRET`). Когда приходит токен, сервер пересчитывает подпись сам и сравнивает. Если совпадает — токен настоящий. Если кто-то изменил данные внутри — подпись не совпадёт и токен отвергнут.

**Stateless — почему это хорошо:**
Сервер не хранит список "кто сейчас залогинен". Он просто проверяет подпись токена. Это значит — сервер можно перезапустить, и все залогиненные пользователи остаются залогиненными.

**В нашем проекте:**
- Токен живёт 7 дней (`expiresIn: '7d'`)
- Хранится в localStorage браузера
- При каждом запросе автоматически добавляется в заголовок: `Authorization: Bearer <токен>`

## Socket.IO — "Живой телефон вместо SMS"

**Простыми словами:**
Обычный HTTP работает как SMS: ты отправил запрос — получил ответ — соединение закрыто. Чтобы узнать новое — надо снова отправить запрос.

Socket.IO — это как телефонный звонок: соединение установлено и остаётся открытым. Сервер может в любой момент сам отправить данные браузеру, без запроса.

**Зачем это нужно в нашем проекте:**
Когда организатор вводит счёт матча 2:1 — все зрители должны видеть это обновление мгновенно, без перезагрузки страницы. Socket.IO отправляет обновление всем подключённым браузерам за доли секунды.

**Комнаты (rooms):**
Чтобы обновление матча видели только участники ЭТОГО турнира, Socket.IO использует комнаты. Пользователь "вступает" в комнату турнира: `socket.join('tournament_5')`. Когда приходит обновление — оно отправляется только в эту комнату.

**Аналогия:**
Групповой чат в WhatsApp. Сообщение приходит только участникам группы, не всем пользователям WhatsApp.

## dotenv — "Секретная записная книжка"

**Простыми словами:**
Файл `.env` хранит секретные настройки: пароль от базы данных, секретный ключ JWT, данные для почты. Этот файл НЕ загружается в GitHub — он только на твоём компьютере.

dotenv читает этот файл при запуске сервера и кладёт всё в `process.env.*` — специальное место, откуда весь код может читать настройки.

**Зачем это нужно:**
Чтобы не писать в коде `password: "mypassword123"` — это видел бы каждый на GitHub. Вместо этого в коде написано `process.env.DB_PASSWORD`, а реальный пароль только в файле .env на сервере.

## node-cron — "Будильник для сервера"

**Простыми словами:**
node-cron запускает функцию по расписанию. Как будильник — каждый день в определённое время.

**В нашем проекте:**
Каждый день в полночь (00:00) запускается проверка: "Есть ли турниры, которые уже должны начаться, но ещё в статусе pending?" Если да — их статус меняется на active автоматически.

Без cron пришлось бы вручную активировать каждый турнир.

## express-rate-limit — "Охранник от брутфорса"

**Простыми словами:**
Брутфорс — когда хакер пробует 1000 паролей в секунду, пока не угадает.
rate-limit говорит: "с одного IP можно попробовать войти не более 5 раз в минуту. После — блокировка."

**В нашем проекте:**
- Логин: 5 попыток в минуту
- Регистрация: 3 попытки в час
- Восстановление пароля: 5 попыток в 15 минут

## crypto — "Генератор случайных токенов"

**Простыми словами:**
Встроенный модуль Node.js. Используется чтобы создать случайный уникальный токен для ссылок в email.

Когда пользователь нажимает "Забыл пароль" — создаётся случайная строка из 64 символов (типа `a3f9c2...`). Она сохраняется в базу и вставляется в ссылку письма. Когда пользователь переходит по ссылке — сервер находит этот токен в базе и разрешает смену пароля.

## CORS — "Разрешение на визу"

**Простыми словами:**
По умолчанию браузер блокирует запросы с одного сайта на другой. Наш фронтенд работает на порту 5500 (Live Server), а бэкенд на порту 3000. Для браузера это разные "сайты".

CORS — это заголовок, который сервер добавляет к ответу: "Разрешаю браузерам с любого источника обращаться ко мне." Без этого браузер заблокировал бы все наши API-запросы.

## Round-Robin — "Все играют со всеми"

**Простыми словами:**
Алгоритм составления расписания турнира, где каждая команда играет с каждой ровно один раз.

**Как работает алгоритм:**
Если 4 команды: A, B, C, D — берём пары:
- Тур 1: A-B, C-D
- Тур 2: A-C, B-D
- Тур 3: A-D, B-C

Математически: фиксируем первую команду, остальные "крутим по кругу" — отсюда название Round-Robin.

**В нашем проекте:**
Функция `generateFixtures()` в `tournamentController.js` автоматически создаёт все матчи при команде организатора.

---

## Playoff (олимпийская система) — "Проигравший выбывает"

**Простыми словами:**
8 команд → 4 матча → победители → 2 матча → финал. Проиграл — всё, вышел из турнира.

**bracket_slot — порядковый номер в сетке:**
Каждый матч знает своё место в сетке. Победитель матча с slot 1 автоматически переходит в следующий матч. Это хранится в поле `next_match_slot` в базе данных.

## backend/server.js — Главный файл, точка входа

**Что делает:**
Это самый первый файл который запускается командой `node server.js`. Он:
1. Создаёт Express-приложение
2. Подключает все middleware (CORS, JSON-парсер)
3. Регистрирует все маршруты (`/api/auth`, `/api/teams`, и т.д.)
4. Запускает Socket.IO
5. Запускает cron-задачу (проверка турниров каждую ночь)
6. Говорит серверу слушать порт 3000

**Простыми словами:**
Это "включить всё" — один файл, который заводит весь механизм.

---

## backend/config/database.js — Соединение с базой данных

**Что делает:**
Создаёт пул из 10 соединений с MySQL. Все контроллеры импортируют этот файл и через него делают запросы в базу.

**Почему пул а не одно соединение:**
Если 100 пользователей одновременно делают запросы — одного соединения не хватит. Пул = 10 параллельных "трубок" к базе.

## backend/routes/ — Маршруты (что можно запросить)

Каждый файл — это группа адресов:
- `auth.js` → `/api/auth/login`, `/api/auth/register`, ...
- `teams.js` → `/api/teams`, `/api/teams/:id`, ...
- `tournaments.js` → `/api/tournaments`, `/api/tournaments/:id/join`, ...
- `matches.js` → `/api/matches`, `/api/matches/:id`, ...
- `statistics.js` → `/api/statistics/global`, `/api/statistics/tournaments/:id`, ...

**Аналогия:**
Маршруты = оглавление книги. Они говорят "глава 3 на странице 45" — но не содержат саму главу.

## backend/controllers/ — Контроллеры (реальная логика)

Каждый файл содержит функции, которые:
1. Читают данные из запроса (req.body, req.params)
2. Делают запрос в базу данных
3. Обрабатывают результат
4. Отправляют ответ (res.json)

**authController.js** — регистрация, вход, выход, восстановление пароля
**teamController.js** — создание команды, добавление игроков
**tournamentController.js** — создание турнира, вступление, генерация матчей, обновление счёта
**matchController.js** — список матчей, детали матча, события матча
**statisticsController.js** — глобальная статистика, статистика турнира

## frontend/js/api.js — HTTP-клиент

**Что делает:**
Это центральный файл для всех запросов к серверу. Вместо того чтобы в каждом файле писать `fetch(...)` с заголовками — всё собрано здесь.

**Главная функция `request()`:**
1. Берёт токен из localStorage
2. Добавляет заголовок `Authorization: Bearer <токен>`
3. Делает fetch-запрос
4. Проверяет ответ
5. Возвращает JSON

**Проверка авторизации (`isAuthenticated()`):**
Смотрит на токен в localStorage, декодирует его (без проверки подписи — просто читает дату истечения) и проверяет: не просрочен ли. Если просрочен — автоматически разлогинивает.

## frontend/js/main.js — "Дирижёр оркестра"

**Что делает:**
Это первый JS-файл который выполняется при открытии сайта. Он запускает всё в правильном порядке:

```
1. I18n.init()         — загрузить переводы
2. UI.init()           — настроить интерфейс
3. Auth.init()         — проверить токен, показать профиль или гостевую страницу
4. Tournaments.init()  — загрузить турниры
5. Teams.init()        — загрузить команды
6. Matches.init()      — загрузить матчи
7. Statistics.init()   — загрузить статистику
8. WebSocketManager.init() — подключить WebSocket
```

**Почему порядок важен:**
Auth должен быть раньше Tournaments — потому что tournamentsController проверяет, залогинен ли пользователь, чтобы показать кнопку "Вступить".

## Что такое таблица и зачем id

Каждая таблица — это список чего-то. Каждая строка имеет уникальный номер (id) — как паспорт. Другие таблицы ссылаются на эти номера.

**Почему id а не имя:**
Имя может измениться, совпасть у двух людей, написаться с опечаткой. Число — всегда уникальное и точное.

# ЧАСТЬ 5 — РЕГИСТРАЦИЯ И ВХОД

---

## Регистрация — шаг за шагом

**Пользователь вводит:** имя, email, пароль, роль → нажимает "Зарегистрироваться"

**Шаг 1: Фронтенд**
`auth.js` → `handleRegister()` берёт данные из формы, вызывает `API.register({name, email, password, role})`

**Шаг 2: HTTP-запрос**
`POST /api/auth/register` с телом `{name, email, password, role}` летит на сервер

**Шаг 3: Rate Limiter**
Сервер сначала проверяет: не слишком ли часто регистрируется с этого IP? (3 раза в час)

**Шаг 4: authController.register()**
- Проверяет: email уже существует в базе? Если да — ошибка
- Генерирует хеш пароля: `bcrypt.hash(password, 10)`
- Генерирует токен для подтверждения email: `crypto.randomBytes(32)`
- Сохраняет пользователя в таблицу users
- Отправляет письмо через Nodemailer со ссылкой активации

**Шаг 5: Пользователь получает письмо**
Письмо содержит ссылку: `http://localhost:3000/api/auth/verify-email?token=abc123...`

**Шаг 6: Подтверждение email**
Пользователь нажимает ссылку → сервер находит токен в базе → ставит `email_verified = 1` → выдаёт JWT токен → перенаправляет на сайт с токеном в URL

**Шаг 7: Фронтенд ловит токен**
`auth.js` → `handleVerificationRedirect()` видит токен в URL (`?token=...`), сохраняет в localStorage → обновляет интерфейс (показывает профиль)

---

## Логин — шаг за шагом

**Пользователь вводит:** email + пароль → нажимает "Войти"

1. `handleLogin()` вызывает `API.login({email, password})`
2. `POST /api/auth/login` летит на сервер
3. Rate Limiter: не больше 5 попыток в минуту
4. `authController.login()`:
   - Ищет пользователя по email в базе
   - `bcrypt.compare(password, hash)` — сравнивает пароль с хешем
   - Если не совпадает → ошибка "неверный пароль"
   - Если совпадает → `jwt.sign({id, email, role}, SECRET, {expiresIn: '7d'})`
   - Возвращает `{token, user}`
5. Фронтенд получает токен → сохраняет в localStorage
6. `updateProfileSection()` — перерисовывает шапку с профилем пользователя

---

## Что происходит при каждом следующем запросе

Когда залогиненный пользователь делает любое действие (загружает турниры, создаёт команду):

1. `api.js` берёт токен из localStorage
2. Добавляет заголовок: `Authorization: Bearer eyJhbGci...`
3. Сервер получает запрос → middleware `authenticateToken` перехватывает
4. `jwt.verify(token, SECRET)` — проверяет подпись
5. Если токен валидный → `req.user = {id: 1, role: "organizer"}`
6. Контроллер использует `req.user.id` чтобы знать кто делает запрос

# ЧАСТЬ 12 — БЕЗОПАСНОСТЬ

---

## SQL Injection — "Взлом через форму"

**Что это:**
Хакер вводит в поле "email" что-то вроде: `admin@mail.com' OR '1'='1`
Без защиты это превратилось бы в SQL: `WHERE email = 'admin@mail.com' OR '1'='1'` — что вернёт всех пользователей.

**Наша защита — параметризованные запросы:**
```javascript
// ОПАСНО:
db.query(`SELECT * FROM users WHERE email = '${email}'`);

// БЕЗОПАСНО (так у нас):
db.query('SELECT * FROM users WHERE email = ?', [email]);
```
mysql2 автоматически экранирует все специальные символы в [email] — SQL-инъекция невозможна.

---

## XSS — "Взлом через вставку скрипта"

**Что это:**
Хакер создаёт команду с названием: `<script>alert('взломан')</script>`
Если вставить это в HTML напрямую — браузер выполнит скрипт.

**Наша защита — escapeHtml():**
```javascript
function escapeHtml(str) {
    return str
        .replace(/&/g, '&amp;')
        .replace(/</g, '&lt;')    // < становится &lt; — браузер показывает символ, не тег
        .replace(/>/g, '&gt;')
        .replace(/"/g, '&quot;')
        .replace(/'/g, '&#039;');
}
```
Все данные от пользователя проходят через эту функцию перед вставкой в HTML.

---

## Rate Limiting — "Защита от перебора"

Уже объясняли: не более 5 попыток входа в минуту с одного IP.

**Почему это важно:**
Без ограничения хакер может перебирать пароли тысячами в секунду. С ограничением — максимум 5 в минуту = 300 в час. Это делает брутфорс практически невозможным.

7. Загружаются данные для каждой секции
8. Страница готова к использованию

# БЫСТРАЯ ШПАРГАЛКА — ОТВЕТЫ НА ЧАСТЫЕ ВОПРОСЫ

---

**"Где хранятся пароли?"**
В таблице users, поле password_hash. Это bcrypt-хеш, не сам пароль. Восстановить невозможно.

**"Как сервер знает кто я?"**
По JWT-токену который хранится в localStorage браузера и отправляется с каждым запросом.

**"Что будет если истечёт токен?"**
`API.isAuthenticated()` проверяет дату. Просрочен — автоматически разлогинивает.

**"Как обновляется счёт матча у всех сразу?"**
Socket.IO. Сервер отправляет событие в комнату турнира, все подключённые браузеры получают его мгновенно.

**"Откуда берутся матчи?"**
Генерируются алгоритмом (Round-Robin / Playoff) при нажатии "Сгенерировать матчи".

**"Почему foreign key а не просто имя?"**
id — уникальное, неизменное, занимает мало места. Имя может поменяться, дублироваться, написаться с ошибкой.

**"Что такое middleware?"**
Функция которая выполняется ДО контроллера. Проверяет что-то (авторизацию, лимит запросов) и либо пропускает дальше, либо возвращает ошибку.

**"Чем отличается league от playoff?"**
League: все играют со всеми, побеждает кто набрал больше очков.
Playoff: проиграл — выбыл, победитель проходит дальше.
Group+Playoff: сначала как league (по группам), потом лучшие играют как playoff.

**"Зачем нужен .env файл?"**
Хранить секреты (пароль от БД, JWT-секрет, данные почты) отдельно от кода. Код идёт на GitHub — .env нет.

**"Как добавить нового игрока в команду?"**
Тренер ищет по имени → система ищет в users WHERE role='player' → тренер выбирает → в таблицу team_players добавляется строка (team_id, user_id).

**"Как работает автоактивация турниров?"**
node-cron запускает функцию каждую ночь в 00:00. Она ищет турниры WHERE start_date <= NOW() AND status = 'pending' и меняет их статус на 'active'.
